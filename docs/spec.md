# Desk AI Tutor（仮称）要件定義・設計仕様書 v2.0

> v1.0からの主な変更点：音声トリガー（ウェイクワード）方式を廃止し、**Bluetoothリモコン**と**画面タップボタン**の2パターンによる明示的トリガー方式に変更。WebRTC接続性・プライバシー開示・失敗時UXに関する対策を追加。

---

## 1. プロジェクト概要・目的

**プロジェクト名**: Desk AI Tutor（手元AI学習アシスタント）

**背景・目的**:
家庭内に眠っている「使わなくなった古いスマートフォン」を再利用し、学習机に固定して専用のAIアシスタント化する。手元のノートや問題集をカメラで捉え、トリガー操作（ボタン）を行うだけで、目の前のPC・タブレットの大画面に解法ステップや数式・図解を自動表示する。高価な専用スマート文具や外部ハードウェアを一切購入せず、完全無料枠のAPIとオープンソース（OSS）構成で誰でも手軽に構築・利用できるようにする。

**v1.0からの設計変更**: 当初検討していた「音声トリガー（ウェイクワード検知）」は、以下の理由からv2.0では不採用とした。

- Android OSの背景実行制約（常時マイク稼働のためのフォアグラウンドサービス・バッテリー最適化除外が必須）により実装・運用コストが高い
- ウェイクワードエンジン（Porcupine等）は日本語カスタムワードの学習に制限（無料枠は1ヶ月1モデルまで）があり、フレーズ変更の柔軟性が低い
- 環境音・家族の会話による誤検知リスク
- 常時マイク稼働は発熱・電池消耗の面でも中古端末に不利
- 物理トリガー（ボタン）の方が「押した＝聞いてほしい」という意図が100%明確で、UXも単純

## 2. サービス方針・設計原則

- **Zero Hardware Cost（追加ハードウェア不要）**: 手持ちの余剰スマホ（Android）と普段使っているPC/タブレットのブラウザ、および数百円程度の市販Bluetoothリモコンのみで完結。
- **Zero Server Cost（管理者サーバー費用0円）**: バックエンドサーバーを常時運用せず、PCとスマホの直接P2P通信（WebRTC）および静的ホスティング（GitHub Pages等）を活用。接続性確保のため無料TURN中継（後述）を併用する。
- **BYOK（Bring Your Own Key）モデル**: 利用者自身が取得したGoogle AI Studio APIキー（無料枠）を使用。管理者がAPIコストやユーザー管理を抱え込まない。
- **Privacy & Local First（プライバシー最優先、ただし限界を明示する）**: 手元ノートの画像やAIの回答データは自前の中継サーバーを経由せず、家庭内LAN（P2P、必要時のみ無料TURN中継）とGoogle Gemini APIとの間のみで完結する。**ただし、無料枠のGemini APIに送信したデータはGoogle側のモデル改善に利用される可能性がある**（有料ティアと異なりデータ利用オプトアウトが保証されない）。この点はREADMEおよび初回起動時の同意画面で利用者に明示する。

## 3. システムアーキテクチャ・通信フロー

```
+-------------------------------------------------------------------------+
| [PC / タブレット] Webブラウザ (GitHub Pagesで開いたSPA)                  |
|  1. QRコード表示 (Room ID / ワンタイム・十分な長さのUUID)               |
|  6. 受信したMarkdown/LaTeXテキストをKaTeX等で大画面レンダリング         |
|  ・ 接続状態インジケータ（接続中/切断/再接続試行中）を常時表示          |
+-------------------------------------------------------------------------+
       ^                                                 |
       | (シグナリング: 接続情報の交換のみ)              | (初回アクセス時のみJS読み込み)
       v                                                 v
+------------------------------+              +-----------------------+
| シグナリング + TURN中継       |              | 静的Webホスティング   |
| (PeerJS Cloud + STUN)         |              | (GitHub Pages/Vercel) |
| + Open Relay Project (無料TURN)|             +-----------------------+
| ※ PeerJS Cloud障害時は        |
|   手動再接続導線でフォールバック|
+------------------------------+
       ^
       | (シグナリング / 必要時はTURN経由で中継)
       v
+-------------------------------------------------------------------------+
| [卓上固定スマホ] Androidアプリ (Flutter)                                 |
|  2. QRコード読み取り -> WebRTC DataChannel (直通 or TURN中継) 確立      |
|  3. トリガー検知（下記2パターンのいずれか、または両対応）               |
|     A) Bluetoothリモコンのメディアボタン押下                            |
|     B) スマホ画面上のタップボタン                                       |
|  4. 高解像度カメラで手元ノートを1枚キャプチャ                           |
|  5. Gemini API (Multimodal) へ直接送信（構造化出力で解答ステップを取得）|
|  ・ フォアグラウンドサービス + 画面OFF運用（画面点灯は不要）            |
+-------------------------------------------------------------------------+
       |
       | 撮影画像 + 構造化リクエスト
       v
+-------------------------------------------------------------------------+
| Google Gemini API (Google AI Studio / gemini-2.5-flash系)               |
|  ・ ノートのOCR・手書き文字認識                                          |
|  ・ ヒント・ステップ解説・LaTeX数式テキストの生成（steps配列で構造化）  |
+-------------------------------------------------------------------------+
       |
       | 回答テキスト (JSON: steps配列 / Markdown・LaTeX)
       v
[卓上固定スマホ] === (WebRTC DataChannel / LAN内直通 or TURN中継) ===> [PCブラウザ]
```

### 通信フェーズの分離

1. **初期ロード**: PCブラウザがGitHub Pagesからフロントエンド（HTML/JS）を一度だけダウンロード。
2. **ペアリング**: PeerJS Cloudを介して接続先情報を交換し、WebRTC P2P回線を確立。STUNで直接接続を試み、失敗時はOpen Relay Project（無料TURN）経由で自動フォールバック。
3. **推論実行**: スマホがGoogle Gemini APIとHTTPS通信を行い、構造化された解法テキスト（JSON）を取得。
4. **画面更新**: スマホからPCへ、WebRTC DataChannel経由でテキストデータを直接プッシュ送信。
5. **状態監視**: `iceConnectionState`を監視し、切断検知時は自動でICE再ネゴシエーション（ICE restart）を試みる。復旧不能な場合はPC画面にQR再表示・再接続導線を出す。

## 4. 機能仕様

### 4.1 スマホ側（Android / Flutter アプリ）

- **画面OFF運用**: 画面は基本消灯（`PARTIAL_WAKE_LOCK`でCPUのみ起こす）。画面点灯はPC側の役割であり、スマホ側で常時点灯させる必要はない。
- **フォアグラウンドサービス化**: `foregroundServiceType="camera"`等を宣言し常駐通知を出す。バッテリー最適化除外（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）を初回起動時にユーザーへ依頼。メーカー独自の電力最適化（自動起動制限等）がある機種では、設定手順をREADMEに明記。
- **ペアリング機能**: PC画面に表示されたQRコード（ワンタイムID）をスキャンして自動接続。
- **トリガー検知（2パターン、設定で切替可）**:
  - **パターンA: Bluetoothリモコン**
    - 市販の安価なBluetoothシャッターリモコン（AVRCP/メディアボタンとして動作するもの）を使用。
    - アプリ内で`MediaSession`を常駐させ、`ACTION_MEDIA_BUTTON`イベントを受信してトリガーとする（フォアグラウンドサービスと同居させることで、画面OFF・バックグラウンドでも確実に受信）。
    - 購入時の注意点として「Android動作確認済み」の製品を選ぶようREADMEに明記（一部の安価なリモコンはiOS専用設計のものがある）。
  - **パターンB: 画面タップボタン**
    - スマホアプリ画面に大きな撮影トリガーボタンを常時表示。
    - リモコン不要で即使える最小構成として、MVPの初期実装対象とする。
  - 両パターンとも、トリガー後の動作（撮影→送信）は共通ロジック。音声認識・ウェイクワード機能は実装しない。
- **カメラ撮影制御**: トリガー発火時のみ、オートフォーカスを合わせて高解像度フレームを1枚キャプチャ（連続ストリーミングは行わず発熱・電池消費を抑制）。簡易前処理（台形補正・コントラスト調整）を実施。
- **Gemini API連携**: 端末ローカルに保存したAPIキーを使用し、キャプチャ画像をマルチモーダルリクエストとして送信。レスポンスは`response_schema`による構造化出力（`steps: [{ order, content, latex? }]`形式）を指定し、モデルの「一気に全解答を出してしまう」挙動をAPI側でも抑制する。
- **P2Pデータ送信**: 取得したAI構造化レスポンスをWebRTC DataChannel経由でPCへ送信。
- **エラーフィードバック**: Gemini APIエラー（429/5xx等）発生時は、対応する状態をP2P経由でPC側に伝え、PC画面に「今日はAPIの利用上限に達しました」等の分かりやすいメッセージを表示（音声フィードバックは行わない）。

### 4.2 PC/大画面側（Web / SPA）

- **ルーム生成 & QRコード描画**: アクセス時にワンタイムかつ十分な長さ（UUID相当）のRoom IDを発行し、ペアリング用QRコードを表示。
- **接続状態インジケータ**: 「接続中」「切断」「再接続試行中」を画面の一部に常時表示し、無反応状態でユーザーを迷わせない。
- **P2Pデータ受信**: スマホからのDataChannel接続を受け入れ、構造化データを待機。
- **リッチレンダリングエンジン**:
  - 数式表示: KaTeX / MathJaxによるインラインおよびブロック数式の描画。
  - 解説表示: Markdown（箇条書き、太字、コードブロック等）の整形表示。
  - **段階的ヒント表示UI**: Gemini側で全ステップが生成済みであっても、PC画面では「次のヒントを見る」ボタンをクリックした分だけステップを開示する。出し方の制御をモデルの指示追従性に依存せず、フロントエンド側で物理的にガードする。
- **APIキー設定UI**: PC側でAPIキーを入力し、ペアリング時にスマホ側へ渡す補助機能（任意）。

## 5. 技術的課題と解決アプローチ

| 課題 | 内容・影響 | 解決アプローチ |
|---|---|---|
| Android背景実行の制約 | 常時稼働・カメラ待機による端末の熱暴走やOSによるタスク終了 | ・トリガー待機はBluetoothリモコンのメディアボタン受信 or 画面タップのみとし、常時マイク・常時カメラ稼働を行わない<br>・フォアグラウンドサービス + バッテリー最適化除外依頼<br>・画面は消灯運用（`PARTIAL_WAKE_LOCK`のみ） |
| 手書き文字・図形の認識精度 | 手元の影、ブレ、斜めからのアングルによるOCRミスの発生 | ・Gemini 2.5系Flashの高精度マルチモーダルビジョンを活用<br>・画像を台形補正・コントラスト調整する簡易前処理<br>・システムプロンプトで「手書きの数式を正確にLaTeXに変換する」よう厳格に指示 |
| P2P接続性（NAT越え・APアイソレーション） | 一部の家庭用Wi-FiルーターはAPアイソレーションを有効にしており、STUNのみでは接続が成立しない場合がある | ・GoogleのパブリックSTUNサーバーに加え、Open Relay Project（無料TURN）をICE設定に追加し自動フォールバック<br>・`iceConnectionState`監視によるICE再ネゴシエーション<br>・PeerJS Cloud障害時に備え、QR再表示による手動再接続導線を必須実装 |
| TURN中継時のプライバシー | 中継業者にIPアドレス・通信量等のメタデータが見える | ・通信内容自体はDTLSで暗号化され、TURN業者は復号できない構造であることをREADMEに明記<br>・メタデータも一切外部に触れさせたくない場合の代替として、自前TURN（coturn）の構築手順もオプションとしてdocsに掲載 |
| Gemini無料枠のデータ利用・レート制限 | 無料枠データはGoogle側のモデル改善に利用され得る／モデルごとにレート制限が大きく異なる | ・READMEおよび初回同意画面でデータ利用条件を明示<br>・Pro系モデル（レート制限が厳しい）ではなくFlash系を既定モデルとする<br>・モデルIDを設定ファイルで切替可能にし、API仕様変更に追従しやすくする |
| 段階的ヒント提供（学習体験） | AIが最初から答えを全て出力してしまう問題 | ・プロンプト指示のみに頼らず、`response_schema`でsteps配列として構造化出力させ、UI側のボタン操作で開示ステップ数を制御する |
| 失敗時のユーザー体験 | 接続断・APIエラー時に無反応でユーザーが混乱する | ・PC画面に接続状態インジケータを常時表示<br>・APIエラー種別ごとに分かりやすいメッセージをPC画面に表示 |
| 中古端末のバッテリー劣化 | 経年劣化バッテリーの膨張・発火リスク | 利用者の端末選定・バッテリー健康度の自己確認に委ねる（README上で常時充電運用時の注意喚起のみ記載） |

## 7. 開発・リリースの進め方（ロードマップ）

### Phase 1: PC側Webビューワーの実装（apps/web）
- PeerJSを用いたRoom ID（ワンタイムUUID）生成・QRコード表示。
- 受信したテキスト（Markdown + LaTeX）をリアルタイムに整形表示するUIの作成。
- 接続状態インジケータの実装。
- GitHub Pagesへの自動デプロイ設定。

### Phase 2: モバイルアプリの基本機能実装（apps/mobile）
- Flutterプロジェクトの立ち上げ、カメラ権限設定。
- QRコードスキャンによるPCとのWebRTC P2P接続確立（STUN + Open Relay TURNフォールバック）。
- **画面タップボタン**による撮影 ＆ Gemini API呼び出し（構造化出力） ＆ テキスト送信。
- APIエラー時のフィードバック表示。

### Phase 3: Bluetoothリモコン対応と信頼性向上
- `MediaSession`によるBluetoothメディアボタン受信対応。
- フォアグラウンドサービス化・バッテリー最適化除外導線の実装。
- ICE再ネゴシエーション・再接続導線の実装。
- 段階的ヒント表示UI（「次のヒントを見る」ボタン）の実装。

### Phase 4: OSS公開・配布整備
- GitHub ActionsでのAPK自動ビルド（Releases配布）設定。
- READMEの作成（導入手順、データ利用に関する注意、トラブルシューティング、デモ動画の掲載）。
- 自前TURN構築手順（オプション、プライバシー重視ユーザー向け）をdocsに追加。
